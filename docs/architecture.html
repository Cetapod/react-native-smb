Architecture

Parallelism at two levels — across tasks via the connection pool, and within one task by pipelining requests on a single SMB session: file chunks, directory walks, and tree operations.

Connection pool

HybridSMB runs up to four SMB operations in parallel through SmbConnectionPool(4). Each slot is one smb2_context — its own TCP socket and full session:

session flow
TCP → NEGOTIATE → SESSION SETUP → TREE CONNECT

Tasks call requestContext(mode), hold a slot for the operator's lifetime, then release via PoolContextHandle. One operator per slot (mutex on the context). Work on different slots runs concurrently.

Slot 0 is UI insurance. Interactive ops never queue behind bulk metadata work. When slot 0 is busy, interactive work overflows to slots 1–3.

Pool vs SMB3 multichannel

The server sees each active slot as a separate client connection — multiple full sessions to the same host/share, not channels bound to one session.

This poolSMB3 multichannel
SessionsOne per slotOne across channels
Server viewN connections1 client, N channels
Slot 0 reserved for UIYes—
Requires server multichannel capNoYes

libsmb2 does not implement SMB3 multichannel. Each smb2_context maps to one file descriptor, so the pool uses independent contexts instead.

Chunk pipeline

Cross-task parallelism is the pool. Within a single transfer, SmbFileIO pipelines up to eight SMB2 READ/WRITE requests on the same smb2_context (kMaxInFlight).

Same connection, same session — credit-based pipelining, separate from slot assignment.

Server-side copy

copyItem and duplicateItem copy file data inside the server, so it never crosses the client's network link:

copy flow
open source, create destination
→ FSCTL_SRV_REQUEST_RESUME_KEY on the source        24-byte key
→ FSCTL_SRV_COPYCHUNK_WRITE on the destination      up to 4 in flight, 16 × 1 MiB chunks each
→ fsync, close
  • Each request stays within the protocol's default server limits (256 chunks, 1 MiB each, 16 MiB total). Progress advances per completed request.
  • If the server rejects the copy before any data has moved (NOT_SUPPORTED, INVALID_DEVICE_REQUEST, NOT_IMPLEMENTED, INVALID_PARAMETER), the file is copied through the client with pipelined READ/WRITE instead. The rejection is remembered for the server and share, shared by every pool slot, so it is probed only once.
  • A failure after data started moving fails the copy; the partial destination is deleted, as with the client copy.
  • Server-side copy only works within one share, which every pool slot uses.

Pipelined tree operations

Recursive delete and copy send one small request per file or folder. Several of them stay in flight on one slot, and each completion may start follow-up requests, which keeps the required order. The first failure or a cancel stops new requests, drains the ones in flight, and still runs cleanup (closing handles, removing partial files).

OperationIn flightOrdering
deleteItem16 requestsFiles and empty folders at once; a folder once its contents are gone; the root folder last
Copy: folders16 requestsA folder once its parent exists
Copy: files8 filesEach file runs open → stat → resume key → COPYCHUNK_WRITE → fsync → close as its own chain

A recursive copy sends its first non-empty file alone to find out whether the server supports server-side copy. If it does, the remaining files are copied 8 at a time; if not, they are copied through the client one after another. Files in progress when a copy fails or is cancelled are removed; finished files stay.

Listing pipeline

listDirectory reads directories with raw QUERY_DIRECTORY requests on one slot — Interactive for maxDepth: 0, Metadata for nested listings — and decodes each reply as it arrives, instead of reading the whole directory before returning:

listing flow
[CREATE + QUERY_DIRECTORY] → QUERY_DIRECTORY … → CLOSE       decode each reply as it arrives
   └ directory within maxDepth: same chain, decoded          expand into children
   └ directory at the limit:    same chain, counted          childCount
   └ per entry (opt-in):        CREATE + QUERY_INFO + CLOSE  security descriptor

Lookups share one connection: up to 16 directory queries and, separately, up to 32 security-descriptor queries in flight. Lookups start in top-level order, and directory queries go on the wire before security descriptors. An entry is ready once its lookups finish — for an expanded directory, also all of its children, whose count becomes childCount without another query, so each directory is opened once. Ready top-level entries are emitted in server order through subscribeEntries.

The same engine backs every other directory walk:

CallerListing
deleteItemWhole tree once, then pipelined deletes
copyItem, duplicateItemWhole source tree once; total size and copy plan come from it
duplicateItem namingParent filtered by the server to "<base> copy*"
getPathInfoNone for files (stat and SD query run together); folders read their own entries once for childCount
